# Preview and backend readiness

What exists on Midnight Preview today, what does not, and what stands between
the current state and a submission that can be checked end to end. Measured
against the working tree on 1 September 2026 by probing the live networks and
reading the deployment tooling — not from the roadmap.

## The short answer

**Nothing is deployed to Preview.** Not the registry, not a referendum, not a
credential. Every deployment record in the repository is for the local
`undeployed` Docker chain. The application code for the Preview path is
complete and unit-tested; what is missing is one funded wallet, one deploy run,
and one hosted backend.

The first hard gate is small and concrete: **the Preview relayer wallet must
finish synchronizing and report positive DUST**, which pays for every
transaction. An unrestricted read-only run on 1 September observed one NIGHT
UTXO already registered for DUST generation. After eight minutes the
unshielded section was current (`42630/42630`), while shielded
(`36775/179871`) and DUST (`43762/179872`) were still replaying their indexer
history. The partial state reported zero DUST, so this is progress rather than
deployment evidence. Once full sync and positive DUST are confirmed, the proof
server, deployment inputs, and hosted backend remain separate gates; none is
being represented as complete.

## The dependency chain, in order

Each step is blocked by the one above it. This is the whole critical path.

### 1. NIGHT and DUST wallet state — **incomplete, needs a full sync**

The Preview relayer's unshielded address derives correctly. The latest
read-only run observed one registered NIGHT UTXO, so do not send more funds
until a fully synchronized status run confirms the current balance:

```
mn_addr_preview1r7lyp9rnaphxpzjhn4u39tggjwt05zl630tekhme9z275rj5p4eqr97gss
```

Run `npm run relayer:status` first. It never submits a transaction and reports
whether the wallet is synchronized, whether NIGHT is registered, and whether
positive DUST is available. If the bounded wait expires, its public sync
cursors show which wallet section is still behind without exposing keys or
transaction contents. Midnight documents a rate-limited
[Preview faucet](https://midnight-tmnight-preview.nethermind.dev/), but do not
request more tNIGHT while the incomplete status already sees a registered coin.

### 2. Register NIGHT for DUST — **only if a full sync reports it unregistered**

```bash
npm run relayer:dust
```

NIGHT alone cannot pay a fee. DUST is generated by NIGHT that has been
*registered* for it, and only the owner of the UTXOs can register them. A
relayer holding NIGHT but unregistered fails every vote at the fee step.
The incomplete 1 September status run already observed its one NIGHT UTXO as
registered, so rerunning this write-capable command is not justified unless a
fully synchronized read-only status contradicts that observation.

> **Known limit that will bite immediately.** The current status sees zero DUST
> coins. Even after generation begins, operating with only one DUST coin can
> make two quick submissions contend and return error 170; waiting does not
> clear the relayer's stale reservation. Confirm several available coins or
> serialise submissions before more than one person uses it.

### 3. A local proof server — **one command**

```bash
docker run -p 6300:6300 midnightntwrk/proof-server:8.1.0
```

Both the deploy script and the relayer point at `http://localhost:6300`.
Nothing can be proved without it.

> **Privacy note that must survive into production.** A proof server sees the
> witness — the voter secret and the choice. For the hosted stack the Compose
> model already gives CICO and the relayer their own isolated proof servers on
> a private network. Never point a citizen's browser at someone else's.

### 4. Deploy the v2 contracts — **one command, needs 16 values**

```bash
npm run deploy:preview
```

`.env.v2.preview` currently supplies 6 of the values the script requires
(`V2_NETWORK_ID`, `V2_ISSUER_ID`, `V2_CREDENTIAL_EPOCH`, and three role
secrets). The script also reads, and will fail without:

`V2_EVENT_ID_HEX` · `V2_REFERENDUM_ID` · `V2_REGISTRY_ID_HEX` ·
`V2_ISSUER_ID_HEX` · `V2_ROOT_PUBLISHER_ROLE_SECRET_HEX` ·
`V2_FIXTURE_HOLDER_SECRET_HEX` · `V2_FIXTURE_HOLDER_BLIND_HEX` ·
`V2_FIXTURE_CREDENTIAL_BLIND_HEX` · `V2_FIXTURE_VOTE_SALT_HEX` ·
`V2_FIXTURE_VALID_FROM` · `V2_FIXTURE_VALID_UNTIL`

The `V2_FIXTURE_*` values are the deploy-time self-check, not production
material. They must not be reused as a real voter's secret.

Output: contract addresses plus a manifest. That manifest is what makes every
downstream step possible.

### 5. Host the CICO service — **needs the VPS**

`cico-service` has no `.env` at all. It is the boundary that talks to Rarimo
and issues credentials, and it cannot run on static hosting. This is what the
VPS is for; the full value list is in
[`../deploy/hostinger/VPS-READINESS-CHECKLIST.md`](../deploy/hostinger/VPS-READINESS-CHECKLIST.md).

### 6. Rebuild the frontend against Preview — **mechanical**

Set `VITE_APP_MODE=preview`, `VITE_CICO_REFERENDA_JSON` from step 4's manifest,
`VITE_PASSPORT_V2_API_URL` to the hosted CICO, and rebuild. The app fails
closed if the catalogue is incomplete, so a half-filled configuration blocks
voting rather than faking it — that behaviour is already tested.

## What is *not* blocking

Worth stating, because it is where the work already went:

- **The contracts compile and their ZK keys exist.** No Compact work is
  outstanding for a Preview deploy.
- **The application code paths are present** for enrollment, credential
  issuance, action authorisation, vote submission and receipt reconciliation,
  with unit/simulator and browser coverage; the exact release-run counts must
  be recorded with the release SHA.
- **Fail-closed routing works.** An enabled-but-incomplete v2 runtime cannot
  fall through to the legacy executor.
- **The deployment topology is designed and reviewed** — Compose model, Caddy
  routing, private networks, the Rarimo DELETE derivative and its patch,
  preflight, rollback and packaging tooling.
- **A static demo artifact exists**, but the hosted bundle predates the current
  journey rebuild. The last recorded hosted-browser pass must be rerun after
  repackaging before the URL is presented as current evidence.

## The honest summary for a submission

The demo is runnable locally and the contracts compile. A legacy static URL
exists but is not current release evidence until repackaged and reverified. The
Preview path is written and tested but **has never run against Preview**, and
the NFC credential path has never run against hardware.

If the submission needs a live Preview transaction, the critical path starts
with Preview NIGHT and is otherwise a few commands. If it needs a real
passport-backed credential, the gap is materially larger and involves two
external approvals that are not in anyone's control here.

Do not describe the Preview or NFC paths as working. Describe them as
implemented, unit-tested, and awaiting the funding and approvals listed above —
which is both true and, given the state of the code, a reasonable position.
